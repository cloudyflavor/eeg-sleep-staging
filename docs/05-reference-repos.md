## 1. 두 레포 다 반쪽이다 — 여기가 우리 기회

## 2. YASA에서 배울 것

### 2-1. 에포크 자르기 — 복사 없이 (zero-copy)

`others.py:452-465`의 `sliding_window()`가 `np.lib.stride_tricks.as_strided`를 씁니다.
30초씩 잘라 새 배열을 만드는 게 아니라 **같은 메모리를 다른 모양으로 보는 뷰**를 만듭니다. 메모리 복사가 0입니다.

> 트레이드오프: `as_strided`는 경계 검사를 하지 않아 잘못 쓰면 메모리를 넘어 읽습니다. 성능과 안전성의 교환입니다.

### 2-2. 특징을 에포크별이 아니라 특징별로 계산

```python
ant.hjorth_params(epochs, axis=1)     # 전체 에포크를 한 번에
sp_sig.welch(epochs, sf, ...)         # 전체 에포크를 한 번에
```

에포크마다 루프 돌며 특징 29개를 뽑는 게 아니라, **특징 하나를 전체 에포크에 대해 벡터화**합니다.
YASA가 하룻밤을 몇 초에 처리하는 이유입니다.

예외 두 개(`perm_entropy`, `higuchi_fd`)는 `np.apply_along_axis`로 루프를 돌고, 이것들이 런타임을 지배합니다.
→ **우리 코드도 순열 엔트로피에서 같은 병목이 있습니다.** 실측해서 비용 대비 가치를 따져볼 만합니다.

### 2-3. Welch에 평균 대신 중앙값

```python
sp_sig.welch(epochs, sf, window="hamming", nperseg=5*sf, average="median")
```

Welch는 조각들의 스펙트럼을 합치는데, **평균 대신 중앙값**을 씁니다.
30초 중 1초에 큰 잡음이 껴도 중앙값은 거의 안 움직입니다. **아티팩트 제거를 따로 안 하고도 견디는 장치**입니다.

> YASA는 실제로 수면 단계 분류 경로에서 아티팩트 제거를 **하지 않습니다**(`art_detect`가 있지만 연결 안 됨).
> 중앙값 Welch가 그 역할을 대신합니다. 우리도 아티팩트 처리를 고민하기 전에 이걸 먼저 볼 수 있습니다.

우리 코드는 `nperseg=4*sf`에 기본 평균입니다. **비교 실험 대상입니다.**

### 2-4. 필터를 채널별로 걸지 않고 한 번에

`staging.py:278`에 주석이 있습니다 — 채널을 한 번에 `mne.filter.filter_data`에 넣으면 필터 계수를 한 번만 계산해서 **약 2배 빠릅니다.**

### 2-5. 정규화를 원본이 아니라 평활본에만 건다 ← 우리와 다름

```python
rollc = features.rolling(15, center=True, win_type="triang").mean()  # 7.5분 중심
rollp = features.rolling(4, min_periods=1).mean()                    # 2분, 과거만
# 이 두 개만 robust_scale(quantile_range=(5,95)) 적용, 녹음 단위
```

**원본 특징은 정규화하지 않고 그대로 둡니다.** 평활한 사본 두 개만 정규화합니다.
저는 전부 z-score했습니다. **차이가 나는 지점이고, 실험으로 확인할 가치가 있습니다.**

또 하나 — `z-score`가 아니라 **`robust_scale(5~95 분위)`** 를 씁니다. 극단값에 덜 흔들립니다.

### 2-6. 인과 평활 vs 중심 평활 — 트레이드오프가 드러나는 지점

- `_c7min`: 중심 평활. **미래 에포크를 봅니다.** 오프라인 분석에서만 가능
- `_p2min`: 과거만 보는 평활. **실시간에서도 쓸 수 있습니다**

두 개를 다 넣어 두면 "실시간 배포 시 어떤 특징이 죽는가"를 바로 답할 수 있습니다.
**면접에서 쓸 수 있는 형태의 설계입니다.**

### 2-7. 모델-특징 이름 계약 검증 ← 가장 어필되는 포인트

`_validate_predict()` (`staging.py:393`)가 예측 직전에 **학습된 모델이 기대하는 특징 이름과 지금 계산한 특징 이름을 양방향으로 대조**하고 어긋나면 에러를 냅니다.

이게 막는 것은 **train/serve skew** — 학습할 때와 서빙할 때 특징이 미묘하게 달라지는 사고입니다.
조용히 틀린 예측을 내는 대신 시끄럽게 죽습니다. **MLOps 관점에서 정확히 어필 포인트입니다.**

### 2-8. CI에 "최소 버전" 잡을 따로 둔다

`.github/workflows/python_tests.yml`이 OS 3종 × Python 3.10~3.13 매트릭스를 돌리는데,
**의존성 최소 버전만 설치하는 잡이 따로 있습니다** (numpy==1.22.4, scipy==1.10.0 …).
"우리 라이브러리는 numpy 1.22부터 됩니다"를 말로만 하지 않고 CI로 증명합니다.

### 2-9. 성능 하한 회귀 테스트

`tests/test_staging.py`가 실제 수면 기록 하나를 내려받아 전체 예측을 돌리고 **`accuracy > 0.80`을 검증**합니다.
싸고 가치가 큰 **모델 회귀 테스트**입니다. 리팩터링하다 성능이 떨어지면 CI가 잡습니다.

### YASA에서 베끼지 말 것

- 특징 추출·모델 I/O·플로팅·추론이 **550줄짜리 클래스 하나**에 다 들어있습니다. 특징 단위 테스트가 불가능합니다
- **타입 힌트가 없습니다** (assert 기반 런타임 검증). 2019년엔 괜찮았지만 지금은 아닙니다
- 모델 선택을 **파일명 정렬**로 합니다 (`np.sort(glob(...))[-1]`)
- `joblib` 피클을 wheel에 담습니다 — 라이브러리 버전이 바뀌면 깨집니다. LightGBM 네이티브 텍스트 포맷이나 ONNX가 낫습니다
- 학습 코드가 다른 레포에 있습니다. **우리는 학습과 추론을 한 레포에 둬야 합니다**

## 3. sleep-linear에서 배울 것

### 3-1. 피험자 그룹 CV — 이 분야가 가장 많이 틀리는 부분

```python
StratifiedGroupKFold(10, groups=patient_id)   # patient_id = psg_file[:5]
```

`psg_file[:5]`로 자릅니다 — **Sleep-EDF의 2박 녹음을 같은 피험자로 묶는 처리**입니다. 우리가 `SC4[XX]`로 하려던 것과 같습니다.

거기에 더해 **고정 held-out 설계**도 있습니다: SC-EDF-78에서 SC-EDF-20을 뺀 것으로 학습하고 SC-EDF-20으로 평가.
SC-EDF-20이 역사적 벤치마크 피험자라 옛 논문과 비교가 됩니다. **분리 여부를 assert로 검증**까지 합니다.

### 3-2. 특징 행렬을 parquet으로 한 번만 캐시

```python
df_feats.to_parquet("../features/sleep-edf__cassette_features_ALL__90s.parquet")
```

float32로 낮춰서 저장하고, 이후 모든 실험은 이 파일을 다시 읽습니다.
**특징 추출(느림)과 모델링(빠름)을 분리**하는 겁니다. 모델 하이퍼파라미터를 바꿀 때마다 EDF를 다시 읽지 않습니다.

> 우리는 npz를 썼습니다. parquet과의 비교는 따져볼 만합니다 — parquet은 컬럼 단위 읽기와 pandas 호환이 강점이고, npz는 의존성이 numpy뿐이라는 게 강점입니다.

### 3-3. 기계가 읽을 수 있는 특징 이름

```
"EEG Fpz-Cz__sdelta__w=30s"
"...__w=30s_shift=-1m"
```

이름을 파싱해서 **윈도 크기별·시프트별로 중요도를 묶어 분석**합니다(노트북 셀 98-100).
"±1분 이웃 정보가 실제로 얼마나 기여하나"를 그림으로 답할 수 있습니다. **작은 설계인데 분석력이 크게 늘어납니다.**

### 3-4. 시간 문맥을 두 방식으로

1. **다중 윈도**: 30초/60초/90초 윈도로 같은 특징을 세 번 뽑음
2. **시프트 컬럼**: 30초 특징을 −1분, −30초, +30초, +1분으로 밀어서 붙임. **녹음 단위로 그룹핑해서 밀기** 때문에 녹음 경계를 넘지 않음

> YASA(평활)와 sleep-linear(시프트)가 다른 선택을 했습니다. **직접 비교할 가치가 있는 지점입니다.**
> 평활은 차원이 적고 노이즈에 강하지만 정보가 뭉개집니다. 시프트는 정보를 보존하지만 차원이 커지고 인접 에포크 상관이 그대로 들어옵니다.

### 3-5. 채널 조사를 먼저 하고 하드코딩

모든 파일의 (신호명, 샘플링레이트) 쌍을 먼저 전수 조사한 뒤 `common_signals`를 정합니다.
데이터셋 안에서도 채널 구성이 다른 파일이 섞여 있을 수 있다는 걸 전제한 방식입니다.

### 3-6. 몽타주 유도를 파이프라인 단계로

MASS 노트북에서 `create_montage(sig1, sig2) = sig1 - sig2` 를 **전처리 파이프라인의 한 단계**로 정의합니다.
바이폴라 유도를 코드에 인라인으로 박지 않고 조합 가능한 단계로 만든 것 — **우리가 EDFX와 HMC의 전극 배치 차이를 다룰 때 참고할 패턴입니다.**

### sleep-linear에서 베끼지 말 것

- **전부 노트북**입니다. 데이터셋별로 같은 파이프라인이 복사-붙여넣기되어 조용히 갈라져 있습니다
- `lfilter` (인과 IIR, 위상 왜곡) — `sosfiltfilt`가 맞습니다 (아래 4절 참고)
- `pandas.resample().mean().interpolate()`로 리샘플링 — 안티에일리어싱이 없습니다. `resample_poly`가 맞습니다
- **메트릭 인자 순서가 바뀐 곳이 있습니다** (`f1_score(preds, y_trues)`). macro-F1엔 무해하지만 `classification_report`에서 precision/recall이 뒤바뀝니다
- 테스트·CI·린트 전무
- poetry.lock 정확 고정이 유일한 설치 경로 — 지금은 python <3.11 요구라 설치가 안 됩니다

## 4. 내가 앞서 정했던 것들에 대한 검증

레퍼런스와 대조한 결과입니다. **맞은 것도 있고 틀린 것도 있습니다.**

| 내 선택 | 레퍼런스 | 판정 |
|---|---|---|
| 6개 대역 (slow/delta/theta/alpha/sigma/beta) | YASA가 **동일** (sdelta 0.4-1, fdelta 1-4, theta, alpha, sigma, beta) | ✅ 우연히 일치 |
| Welch PSD로 대역파워 | 둘 다 동일 | ✅ |
| 광대역 0.3–35 Hz | YASA 0.4–30, sleep-linear 0.4–30 | ⚠️ 조정 검토 |
| 전체 특징 z-score | YASA는 **평활본만** robust_scale | ❌ **다름. 실험 필요** |
| 이동평균으로 시간 문맥 | YASA는 평활, sleep-linear는 **시프트** | ⚠️ 둘 다 존재. 비교 필요 |
| `sosfiltfilt` (영위상) | sleep-linear은 `lfilter` (**인과**) | ⚠️ 아래 참고 |
| wake 30분 절단 | sleep-linear 동일 (60 에포크) | ✅ |
| 피험자 단위 CV | sleep-linear 동일 | ✅ |
| 클래스 가중치 | sleep-linear의 CatBoost는 **가중치 없음** | ⚠️ 필요 여부 실험 필요 |

**`lfilter` 건은 짚고 넘어가야 합니다.** 저는 "인과 필터는 위상 왜곡이 있으니 틀렸다"고 말씀드렸는데,
DeepSleepNet을 이긴 sleep-linear이 바로 그 `lfilter`를 씁니다. 즉 **위상 왜곡이 성능에 치명적이지 않다**는 반례입니다.
30초 에포크 안의 통계량(분산, 대역파워)은 위상에 둔감하기 때문일 가능성이 큽니다.
제 주장은 이론적으로 맞지만 **실증적으로 중요한지는 별개**이고, 이건 실제로 A/B 해볼 만한 질문입니다.

## 5. 실험으로 답할 수 있는 질문들 (포트폴리오 소재)

레퍼런스끼리 선택이 갈리는 지점 = 근거를 만들 수 있는 지점입니다.

1. **정규화**: 전체 z-score vs 평활본만 robust_scale vs 정규화 없음
2. **시간 문맥**: 평활(YASA) vs 시프트(sleep-linear) vs 둘 다 vs 없음
3. **필터**: `sosfiltfilt` vs `lfilter` vs 필터 없음
4. **Welch 집계**: 중앙값 vs 평균, `nperseg` 4초 vs 5초
5. **클래스 불균형**: 가중치 vs 없음 (DS가 6.7%뿐인 우리 상황에서)
6. **비싼 특징의 값어치**: `perm_entropy`·`higuchi_fd`가 런타임을 지배하는데 macro-F1에 얼마나 기여하나
7. **채널**: Fpz-Cz vs Pz-Oz vs 둘 다

각각 "비교했더니 이랬다"를 만들 수 있고, 동시에 트레이드오프(정확도 vs 계산비용 vs 실시간 가능성)를 말할 수 있습니다.
